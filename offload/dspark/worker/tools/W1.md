# W1 isolated profiling

No production source or service is changed by these tools. On x86host, sync this
worktree into `~/dsv41-offload/w1/repo/`, reuse the pinned O2 venv, and run:

```bash
source ~/.config/ndm/paths.sh
cd ~/dsv41-offload/w1/repo/offload/dspark
export CUDA_VISIBLE_DEVICES=GPU-c4e7a371-d8a8-ebf0-918c-da3e38c87a93
test -f ~/dsv41-offload/W1_GPU_OK || exit 78
~/dsv41-offload/o2/venv/bin/python -m worker.tools.profile_current \
  /opt/dsv41/x86host-data/dspark ~/dsv41-offload/w1/results/profile-burst \
  --revision "$(cat ~/dsv41-offload/w1/SOURCE_REVISION)" --cupti
```

Run long work detached in a W1-owned tmux session. Revoke the marker to stop
between samples (also checked before/after capture and before diagnostic work).
The tool refuses any other GPU selection, missing telemetry, graph/eager output
differences, and a process footprint >=9 GiB. Never open the marker yourself.
Use a fresh output directory for each run; partial JSONL and summary checkpoints
survive failure. Repeat with `--cadence-ms 42` to inspect duty-cycle clock effects.

The matrix covers B=1–4, n_out=1–5, one/six inserted rows per request and forced
first-position Markov hit/miss. Later positions use actual generated IDs; every
case saves per-position hits and all 128 expert row counts at each stage.
Synthetic taps and tokens are saved on x86host before measurement. This is a
compute/staging experiment; it does not model legal routing distributions,
transport, frame validation, payload packing, or the complete server handler.
The host/device buffers are reused, unlike some production backend allocations.

Each raw sample has CPU timestamps and CUDA events spanning H2D, context insert,
draft, reply packing and synchronous D2H. Both modes use the production insert
graph; only the draft is eager in the eager column. CPU submission and wait times
are reported directly. `wall_minus_gpu_us` is computed per sample before
reduction; it is a residual including scheduling/event overhead, not pure CPU
time. Mode percentiles are separate distributions: subtracting them is not a
paired graph/eager saving. CUPTI totals are a separate kernel-share diagnostic,
not the critical path. Telemetry samples active SM/memory clocks and power every
~100 ms; no settings are changed. Margin graphs are captured for the memory
budget but this timing matrix measures plain replies.

GPU measurements and source-backed donor audits have separate status. CPU tests
passing does not qualify a CUDA implementation or a deployment winner.
